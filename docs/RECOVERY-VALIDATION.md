编译 0 警告、0 错误；原有端到端 173 条断言通过；最终 EXE 的 20 项恢复测试及界面/托盘自检通过。模拟确认额外等待为 0.095～1.144 秒，满足 4/6 秒验收目标。

## 问题与修复

| 问题 | 原因/证据 | 本版处理 |
| --- | --- | --- |
| 提交后确认慢 | 基线 Engine.WaitForRecovery 将等待、状态查询、两轮内容检测串行叠加；“恢复耗时”累计休眠而非真实经过时间 | 实际 30 秒观察窗口，内容单轮每 2 秒，Portal 独立六档；单调计时 |
| 误报恢复 | 基线 Engine 中 confirm.Online / check.Online 可直接结束恢复 | HTTP 配置必须通过期望内容或状态码；会话在线单独记录 |
| 慢目标拖住成功目标 | 基线探测等待其他目标结束 | 任一 HTTP 内容成功即返回并取消剩余；未完成不计失败 |
| 后台任务/过期结果 | 超时与取消需要覆盖整轮，不能让旧任务写回新状态 | 探测截止时间、私有结果、取消令牌、配置代次校验，最多八个探测工作任务 |
| 上游分支长时间不复查 | 基线全部探测失败但 Portal 在线时返回 UpstreamProbeSeconds，默认 300 秒 | 本地仍按异常频率检查，300 秒仅限该分支的会话查询 |
| 手动或自动注销后才发现限频 | 注销在登录闸门之前 | 所有入口先检查凭据、暂停、最小间隔、小时上限，再允许注销 |
| 重载丢失新计数 | Reload 从磁盘 CopyFrom 覆盖内存状态 | 初次启动才载入状态；界面编辑独立副本，保存重载后才生效，保留计数并取消旧流程 |
| 登录计数持久化滞后 | 旧计数和持久化顺序可能漏记被中断的提交 | 每次 POST 前登记并持久化；被打断时允许保守多占一次额度 |
| 同一故障重复自动注销 | 残留会话标记会在尚未恢复时被清除 | 本次故障实际恢复后才清除，期间最多一次自动注销重登 |
| 状态文件并发写冲突 | 新测试复现替换失败后“删除 + Move”与另一保存交错，报“文件已存在” | 同进程保存串行化，读取允许原子替换，替换失败保留有效旧文件 |
| CLI 立即重连时序 | 后台线程先启动，可能先完成其他轮次 | 先登记重连，再启动线程 |
| 自检留下真实后台流程 | 基线 --selftest 同时启动自动登录与守护 | 自检仅构建和刷新界面，不启动登录、重启注册或守护 |

## 恢复调度

1. 收到登录响应后，立即开始 30 秒观察窗口并发起内容校验。
2. 内容校验每 2 秒安排一轮，每类最多一个在途任务；慢轮次结束后再安排，整轮有截止时间。
3. Portal 在窗口第 2、5、9、14、20、23 秒独立调度，最多六次；错过的档位跳过，不集中补发。
4. 内容成功即确认联网并取消其余任务，不等待慢 Portal。全进程状态请求也有上限，避免取消后系统 DNS 延迟积累后台请求。
5. 窗口结束继续按异常频率监视。每小时和最小登录间隔限制 POST，不让本地检查跟着停止。
6. 只有 TCP/ICMP 的旧配置需“传输探测通过 + Portal 在线”，显示“未验证内容”。

- 每种延迟恢复模拟只提交一次登录、未注销；观察期会话查询均不超过六次。慢目标在登录后延迟八秒；慢 Portal 延迟十二秒。成功内容目标在本地立即返回，处于不超过 200 毫秒的验收条件内。
- 最终 EXE 界面/托盘自检正常退出，265 字状态文本被安全压缩至 63 字；没有产生 crash.log、watchdog.log 或提交登录。

## 构建、复现与校验

Windows 环境，准备 .NET 8 SDK 和 .NET Framework 4.8 引用程序集后，在源码根目录运行：

    powershell -ExecutionPolicy Bypass -File build/Build-CampusNet.ps1

该命令编译、生成 dist/CampusNet.exe 与两种校验文件，然后运行原有端到端测试和新增恢复行为测试。也可分别运行：

    powershell -ExecutionPolicy Bypass -File build/Test-CampusNet.ps1 -Exe dist/CampusNet.exe
    powershell -ExecutionPolicy Bypass -File build/Test-Recovery.ps1

## 升级与实机验收

1. 从旧版托盘菜单退出，保留 %LOCALAPPDATA%/CampusNet 数据目录。
2. 核对 SHA256SUMS.txt 后运行新 EXE；已有账号和配置可继续使用。需要替换已安装版本时点“安装”。
3. 采用自然掉线样本，分别记录“首次观察到异常 → 提交”“POST 返回耗时”“提交 → 联网验证通过”。
4. 如需测量真正的确认延迟，应同步采集独立内容请求成功时刻；只有程序日志无法知道网络实际何时恢复。
5. 比较多个样本的中位值和较慢样本，并记录是否有多次 POST、注销或等待限频。

本版已在用户本机部署并作为 2.2.0-pre.1 预发布上线。强制 en_md5=1 的认证协议仍需专门适配；“今日登录”“恢复耗时”界面行保留原来的占位，阶段时间从日志查看。
